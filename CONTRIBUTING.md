# Contributing

Thank you for helping improve OCEAN. This repository describes an experimental methodology; careful criticism and negative results are as valuable as proposals for new features.

## Principles for contributions

- Distinguish hypotheses, implementation proposals, and demonstrated results.
- Describe the failure mode or problem a change addresses.
- Prefer precise, testable language over claims of universal optimality.
- Preserve hard boundaries for security, privacy, budget, and authorization.
- Include counterexamples and note where existing practices may work better.
- Avoid adding process steps unless they create measurable value.

## Proposing a change

For substantial changes, open an issue or discussion describing:

1. The problem and affected scenario.
2. The proposed rule or model change.
3. Expected benefits and costs.
4. Risks, edge cases, and alternatives.
5. How the proposal could be evaluated.

## Evidence

When reporting experimental results, include the task set, baseline, model/tool versions, permissions, budgets, number of trials, metrics, and known limitations. Do not report a single successful demonstration as proof of general improvement.

## Documentation style

Use descriptive headings, define specialized terms, separate normative rules from recommendations, and link to the relevant document. Keep examples explicitly labeled as hypothetical unless they are real measured results.
